# Incidents

CLAUDE.mdから移設した実例集。順位の上下に関わらず踏む罠であることを示す
教材ゆえ、要約せず原文のまま収める。将来CLAUDE.mdから移す他の実例も
本ファイルへ追記していく。

## cmd_171: 番犬が古いコードで6時間走った件

本節はCLAUDE.md「常駐デーモンの再起動」の実例である。

**実例（cmd_171）**: `baton_watchdog.sh`（常駐デーモン）の起動時刻
（09:31:22）とその修正PR #17のマージ時刻（09:37:16）が**わずか6分差**
であったため、supervisorが自動起動した番犬が「修正が入る前のコード」
を掴んだまま6時間以上走り続けた。証拠: `logs/baton_watchdog.log`が
毎サイクルのログ出力を追加したはずのPR #17後もなお0バイトのまま
だったこと。

**【将軍の落ち度として記録する事実】** 将軍は前夜「マージしたことと
動いているものが新しくなったことは別」という教訓を既に申し渡していた
が、今朝その番犬が起きた時刻と修正の着地時刻を突き合わせず、6分の差を
見落とした。**教訓を条文化するよう命じた当人が、その教訓を自ら実行
しなかった実例**であり、これを以て本条の重みとする。

## cmd_209: 起動時刻が新しくとも旧コードが走り続けた件

本節もCLAUDE.md「常駐デーモンの再起動」の実例である。

**実例（cmd_209）**: PR #94（`30211a9`）は04:28:34にGitHub上で
マージされた。inbox_watcher群は07:26:23に起動し、これは現行条文の
検査（起動時刻 vs マージ時刻）を通過する——起動がマージより後だから
である。だが実際にローカル作業ツリーが`30211a9`を取得（pull）した
のは07:29:33、**入替の3分10秒後**であった。プロセスが読んだのは
起動した瞬間のディスクであり、その3分10秒後のディスクではない。
ゆえに「起動時刻 > マージ時刻」が成立していてもなお、走行中の
inbox_watcher 10本は旧`agent_is_busy_check`を保持したまま動き続けた
（cmd_209 AC2 未充足）。**起動時刻が新しいことは、新コードで
動いていることを意味せぬ。**cmd_171では「起動がマージより前」だった
ために古いコードを掴んだが、本件は「起動がマージより後」であっても
なお古いコードを掴み得ることを示す——両者は同じ罠の異なる現れである。

## cmd_221付随: ntfyトピック露出——設定を書いただけでは終わらなかった件

本節は「常駐デーモンの再起動」節の教訓が、コード修正ではなく
**セキュリティ事案の収束**という別の場面でそのまま効いた実例である。

**発端（2026-08-09 09:49）**: cmd_221 PR#102が追加したテストfixtureに、
実際のqueueスナップショット（ntfyトピック名`shogun_furufurure`を含む
実データ）が逐語コピーされたまま公開リポジトリ`yfmaru/multi-agent-shogun`
へ露出した。fixtureは合成データへ差し替え・force-with-lease pushで
是正したが、**孤児commit（差し替え前の旧commit）はGitHub上に残り、
公開イベントAPIから誰でもSHAを辿って読める**ことが将軍実測で判明した
（force-pushは「見えなくした」のではなく「参照から外した」だけ）。
ntfyは既定で無認証のため、トピック名が漏れれば誰でも主の端末へ
なりすまし通知を送れる。

**唯一の確実な収束手段はトピック名の変更**と判断されたが、ここで
「常駐デーモンの再起動」節と同じ罠が現れた:

主は当初`config/settings.yaml`の`ntfy_topic`を新トピック
（`ntfy_feu_chang`）へ書き換えた。**だが設定を書き換えただけでは、
旧トピックを購読し続けるntfy listenerプロセスが生き残り、なりすまし
通知の受け口は開いたままだった。** 設定ファイルは「新しいコード」に
相当し、走り続けるプロセスは「古いコードを掴んだままのデーモン」に
相当する——構造は同一である。

**是正**: 旧listener2体（PID 2754182/2754337、前夜00:25:58起動）を
停止し、新設定を読み込んだ新listenerを起動（親2176568・子2176581、
13:50:56起動、疎通テスト済み）。**この「旧listenerの停止」こそが
本件で最も効いた一手であった**——設定変更単独では、なりすまし通知の
受け口という実害は一切減っていなかった。

**将軍ご自身の失敗2件（記録として残す）**:
(a) 確認パターンの誤り: 起動確認を相対パスでのgrep固定で行ったため、
実際には起動していたプロセスを誤って「失敗」と判定し、二重起動を招いた。
(b) 誤った前提: 「子プロセスは親の終了に従う」と思い込んでいたが、
実際にはppid=1（init）へ引き取られ生き延び、追加のkillが必要だった。
setsid/nohupで起こした常駐は親殺しだけでは止まらぬ。

**教訓**: 「常駐デーモンの再起動」節の規律（設定・コードを書いた
だけでは完了とせず、走っているプロセスの入替・実測確認までを完了
条件とする）は、通常の機能改修だけでなくセキュリティ収束作業にも
そのまま適用される。**「設定ファイルを直した」は「効いている」の
証明にならない**——この一般則が、平時のバグ修正と有事のインシデント
対応の両方で同じ形で罠になることを、本件は示している。
なお、漏れたトピック名自体（孤児commit経由でGitHub公開APIから読める
事実）は技術的に消去できていない。GitHub Supportへのpurge依頼は
実施していない——忘れたのではなく、「トピック変更により旧名は無価値化
したため実害無し」との将軍判断で、意図的にやらぬことを選んだ。

## cmd_231/cmd_232: QC全項目がホストで実行され、コンテナ側のglibc要求を見逃した件

本節はCLAUDE.md「コンテナ化アプリの検証は、そのイメージの中で行う」の実例である。

**発端（cmd_231）**: SlotRecordAppのsqlite3依存を5.1.7→6.0.1へ更新するPRの
QCで、軍師は9経路のバイト単位A/B一致・tarball全体diff・npm audit 0件・
既存テスト178件緑・CI緑の5項目でPASSと判定した。だが本番投入後、
コンテナが `GLIBC_2.38' not found` で再起動ループに陥った（cmd_232）。

**検分の結論（gunshi_rca_232_qc_container_gap）**: 軍師は環境の同一性を
「考えなかった」のではなく、**考えた上でNodeバージョンという単一の変数
のみを揃え、それが一致していることをもって『同一』と結論した**。
QC実施6項目のうち4項目（sqlite3互換性・本番DB A/B実証・既存テスト・CI）が
実行場所に依存する検査であったが、**その4項目すべてがホスト（WSL、
glibc 2.43）またはCIランナー（同種の環境）で実行され、対象コンテナ
イメージ（Debian bookworm、glibc 2.36）の中で実行されたものは0件で
あった**。単一の環境変数（libc版）が、4つの独立に見える証拠を同時に
無効化していた。

見逃した証拠は当時すでに軍師自身のディスク上に在った——cmd_231のQC時に
導入したnode_sqlite3.node（6.0.1）に`objdump -T`を一行当てるだけで
`GLIBC_2.38`が即座に検出できた。docker不要・数秒で済む検査であり、
かつ基準線（develop側、`GLIBC_2.4`要求）と並べれば要求の跳躍
（2.4→2.38）は見落としようがなかった。

**教訓**: 「テストが通る」「本番データでA/B比較した」という証拠の緻密さは、
実行場所の妥当性を保証しない。ネイティブモジュールが要求する環境
（glibc版等）は`package.json`の`engines`のような宣言フィールドには
現れず、ELFヘッダの中にしか存在しない——ゆえに宣言の照合だけでは
原理的に不十分であり、**現物のバイナリを読むか、現物を本番の土壌
（コンテナイメージの中）で動かす**のいずれかが要る。これは「常駐
デーモンの再起動」節が問う時間軸（いつのコードか）とは直交する
空間軸（どこで動かしたか）の問題であり、既存条文の射程外であった
ため新設条文（CLAUDE.md「コンテナ化アプリの検証は、そのイメージの
中で行う」）で塞いだ。
