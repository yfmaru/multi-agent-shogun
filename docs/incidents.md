# Incidents

CLAUDE.mdから移設した実例集。順位の上下に関わらず踏む罠であることを示す
教材ゆえ、要約せず原文のまま収める。将来CLAUDE.mdから移す他の実例も
本ファイルへ追記していく。

## cmd_171: 番犬が古いコードで6時間走った件

本節はCLAUDE.md「常駐デーモンの再起動」の実例である。

**実例（cmd_171）**: `baton_watchdog.sh`（常駐デーモン）の起動時刻
（09:31:22）とその修正PR #17のマージ時刻（09:37:16）が**わずか6分差**
であったため、supervisorが自動起動した番犬が「修正が入る前のコード」
を掴んだまま6時間以上走り続けた。証拠: `logs/baton_watchdog.log`が
毎サイクルのログ出力を追加したはずのPR #17後もなお0バイトのまま
だったこと。

**【将軍の落ち度として記録する事実】** 将軍は前夜「マージしたことと
動いているものが新しくなったことは別」という教訓を既に申し渡していた
が、今朝その番犬が起きた時刻と修正の着地時刻を突き合わせず、6分の差を
見落とした。**教訓を条文化するよう命じた当人が、その教訓を自ら実行
しなかった実例**であり、これを以て本条の重みとする。

## cmd_209: 起動時刻が新しくとも旧コードが走り続けた件

本節もCLAUDE.md「常駐デーモンの再起動」の実例である。

**実例（cmd_209）**: PR #94（`30211a9`）は04:28:34にGitHub上で
マージされた。inbox_watcher群は07:26:23に起動し、これは現行条文の
検査（起動時刻 vs マージ時刻）を通過する——起動がマージより後だから
である。だが実際にローカル作業ツリーが`30211a9`を取得（pull）した
のは07:29:33、**入替の3分10秒後**であった。プロセスが読んだのは
起動した瞬間のディスクであり、その3分10秒後のディスクではない。
ゆえに「起動時刻 > マージ時刻」が成立していてもなお、走行中の
inbox_watcher 10本は旧`agent_is_busy_check`を保持したまま動き続けた
（cmd_209 AC2 未充足）。**起動時刻が新しいことは、新コードで
動いていることを意味せぬ。**cmd_171では「起動がマージより前」だった
ために古いコードを掴んだが、本件は「起動がマージより後」であっても
なお古いコードを掴み得ることを示す——両者は同じ罠の異なる現れである。
